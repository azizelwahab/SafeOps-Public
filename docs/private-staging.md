# Private staging runbook

Status as of November 26, 2026. Preparation only. Provisioning, GitHub App authorization, DNS changes, spending, and any route publication require product owner approval.

## Recommended hosting

Use a Render Starter **Private Service** named `safeops-staging` for Express and the built-in frontend. Run `cloudflared` in a Starter **background worker** named `safeops-staging-tunnel`, in the same Render workspace, region, and staging network as Express. Render authorizes the worker to initiate private-network connections. Set `PORT=10000` on Express and copy the exact value from **Connect → Internal** on the app service. Configure the tunnel origin as HTTP with that address and port, for example `http://safeops-staging-xxxx:10000`. The example is illustrative; use the dashboard's actual address. Express already binds on all interfaces by default. Use a Private Service to avoid a public Render hostname. [Render Private Services](https://render.com/docs/private-services), [Render private networking](https://render.com/docs/private-network).

Pin the connector image version or digest and use its `cloudflared tunnel --no-autoupdate --protocol http2 run` command with `TUNNEL_TOKEN` injected only into the worker. HTTP/2 uses outbound TCP 7844. Verify worker DNS resolution, internal TCP connectivity to the app, and the tunnel's connected status. A running connector process is required. A separate paid worker is required for **this** two-service layout, but is a design choice: a supervised connector on the app's host can share its compute and target loopback. That option needs a custom image or supervisor, independent restart handling, signal forwarding, and a separate failure test. A connector on a laptop cannot resolve or reach a Render-only address without a separately designed private connection. [Cloudflare run parameters](https://developers.cloudflare.com/tunnel/reference/run-parameters/), [Cloudflare network requirements](https://developers.cloudflare.com/tunnel/configuration/).

Create a Cloudflare Access self-hosted application for the entire approved staging hostname before enabling its tunnel route. Allow only named identities with MFA and grant a separate, scoped service identity to health probes. Enable **Protect with Access** on the tunnel origin and verify its `access.required`, `teamName`, and `audTag` match the staging application. Deny unmatched ingress and avoid alternate domains, quick tunnels, public previews, and public Render Web Services for the same origin. A private Render origin is reachable by peers on its private network, so keep staging in a dedicated workspace or use a Pro-or-higher isolated environment, including for production separation. The two environments need distinct connector tokens and Access applications. [Cloudflare private web applications](https://developers.cloudflare.com/cloudflare-one/setup/secure-private-apps/private-web-app/), [Cloudflare identity-gated edge](https://developers.cloudflare.com/reference-architecture/design-guides/identity-gated-edge/), [Render private networking](https://render.com/docs/private-network).

The browser uses HTTPS to Cloudflare, the connector tunnel is encrypted, and the connector reaches Express over the Render private network. The final connector-to-Express hop uses private-network HTTP in this design. If policy requires encryption on that hop as well, add and validate an internal TLS hop before staging approval. PostgreSQL clients use the provider's full **external TLS hostname**. Replace the default external allowance with approved app and migration/backup egress ranges. Shared Render outbound CIDRs cover other workloads in the region and are only a network filter. The provider's external allowlist applies only to the external hostname. Enforce private-network isolation separately and assess dedicated egress before accepting sensitive data. [Render Postgres connections](https://render.com/docs/postgresql-creating-connecting), [Render egress ranges](https://render.com/docs/outbound-ip-addresses).

### Simpler private demonstration

For a live portfolio walkthrough, run SafeOps and isolated synthetic PostgreSQL fixtures locally and share the browser screen in an invitation-only meeting. Incremental hosting, DNS, and connector costs are $0 on existing equipment. Participants do not get an interactive endpoint, and the demo does not validate hosted TLS, access controls, or backups. Use hosted staging only if reviewers need independent browser access or the team needs deployment evidence. Render Free is a poor substitute for this private topology: free web services idle after 15 minutes and cannot receive private-network traffic, and free databases expire after 30 days without managed recovery. [Render Free limits](https://render.com/docs/free), [Render recovery](https://render.com/docs/postgresql-backups).

Use separate projects, databases, Access policies, database roles, secret groups, and deploy identities for staging and production. Before production, require verified network isolation across environments; Render workspace private-network access can cross environments unless isolation is configured. Staging holds synthetic data only. Production sizing and availability requirements are a separate approval. [Render private networking](https://render.com/docs/private-network), [Render plan features](https://render.com/docs/platform-features-by-plan).

## Gates before enrolling testers

1. **Owner authorization.** Approve the cost ceiling, region, isolation model, named tester list and MFA policy, registrar/DNS change, GitHub App access, and staging route. Decide whether HTTP inside the isolated Render network meets the encryption policy. Approve the hosting steps separately from opening access.
2. **Ingress and connector evidence.** Prove the worker reaches only the intended staging origin over Render's internal address. Test full-host Access enforcement, origin audience validation, and absence of any direct public Render URL. Verify edge throttling under the chosen plan and the app's shared limiter behavior before opening.
3. **Database evidence.** Verify externally allowlisted egress, runtime and migration TLS with their distinct clients, least-privilege grants, and a successful migration against the intended staging database. Choose a Render-supported PostgreSQL version and run the workflow there. The local development server and hosted PostgreSQL can use different major versions.
4. **Operational evidence.** Approve and rehearse the operator provisioning and recovery jobs, run an isolated restore drill, and show that probes and alerts work through the approved topology. Capture the completed smoke checklist before asking the owner to admit testers.

## Deployment checklist

- [ ] Obtain owner approval for the staging budget, region, workspace isolation, service creation, domain and exact DNS change, GitHub App access, authorized identities, and route publication. Confirm the private-network HTTP hop is acceptable or design verified TLS for that hop.
- [ ] Keep GitHub private. Scope the approved GitHub App to SafeOps, disable automatic deploys and public previews, and record the approved commit SHA. Pin a tested Node release from the package engine range. Build with `npm ci --include=dev` and `npx --no-install prisma generate`. Start with `npm start` and `PORT=10000` on the Private Service. [Render Git provider setup](https://render.com/docs/git-provider).
- [ ] Provision the staging database, restrict external access, and verify the provider hostname, database, connected role, and TLS on the migration connection. From the isolated migration job run `npx --no-install prisma migrate status`, `npx --no-install prisma migrate deploy`, then `npx --no-install prisma migrate status`. Inject its `DATABASE_URL` only into that job. Never run integration tests against hosted staging.
- [ ] Apply and verify runtime grants. Start the app with runtime-only secrets. From the private network, verify that the app answers on the dashboard's Internal address and that readiness returns 200. From an off-network connection verify that Render exposes no alternate app origin or preview that reaches SafeOps.
- [ ] With the Access policy already in place, start the approved connector and enable the authorized staging route. Check TLS, deny-by-default behavior, the origin's Access audience check, and denial of direct or alternate access. Confirm unauthenticated clients cannot receive SafeOps content from either the browser or API path.
- [ ] Rehearse provisioning, recovery, and restore with synthetic data, confirm monitored liveness and readiness, and complete the smoke tests below. Obtain separate owner approval to admit testers. Reserve production for a later approval with separate credentials and infrastructure.

### PostgreSQL privileges

Create separate LOGIN roles per environment with no cluster-wide `SUPERUSER`, `CREATEROLE`, `CREATEDB`, replication, or row-security bypass. The migration identity needs `CONNECT`, ownership of the SafeOps schema objects and migration metadata, and permission to create objects in the designated `public` schema. The initial migration explicitly creates `public` if absent, so allow creation in the designated database for that step if required by the provider. Keep that privilege off the runtime role. The provider owner manages role creation and grants in a separate operator session. Use secret injection or a masked prompt for role credentials. After migration, scope the following grants to the designated SafeOps database and run them as the appropriate owner.

```sql
GRANT CONNECT ON DATABASE safeops_staging TO safeops_runtime;
GRANT USAGE ON SCHEMA public TO safeops_runtime;
GRANT SELECT ON TABLE "Organization" TO safeops_runtime;
GRANT SELECT, INSERT, UPDATE ON TABLE "User", "Hazard", "RiskAssessment", "CorrectiveAction" TO safeops_runtime;
GRANT SELECT, INSERT ON TABLE "AuditLog", "RiskAssessmentRevision", "CorrectiveActionEvent",
  "ResidualRiskRevision", "HazardClosureDecision" TO safeops_runtime;
```

Give runtime no ownership, superuser, role creation, database creation, schema creation, or direct access to `_prisma_migrations`. Remove broad inherited application grants on the target and verify the effective grants, including `PUBLIC` privileges. SafeOps locks selected user and hazard rows, so its existing mutation flows need those tables' update privileges. Audit and revision tables remain append-only for the runtime. Recheck the grant list after each migration. Verify server address/TLS, effective role, schema ownership, and required transaction flows with disposable staging data.

### PostgreSQL TLS by client

| Client | Required URL settings |
| --- | --- |
| Express runtime, using `@prisma/adapter-pg` and `pg` | External managed hostname on port 5432 and `sslmode=verify-full`. Use Node's trust store or the appropriate client CA file. The internal Render hostname uses a self-signed certificate and Render documents that it does not support this mode. |
| Pinned Prisma 7.10.1 migration and migration-status job | Same external hostname, separate migration login, and `sslmode=require&sslaccept=strict` using the job's OS trust store or Prisma's supported `sslcert` CA file option. The native migration engine treats `verify-full` as an unrecognized mode and defaults to `prefer`. A local no-TLS probe reproduced plaintext fallback with `verify-full` and confirmed no fallback with `require&sslaccept=strict`. |
| PostgreSQL backup and restore utilities | External hostname and libpq `sslmode=verify-full` with the applicable system trust setting or CA file for the installed libpq. Keep their role and credentials separate and limit them to the approved backup or restore task. |

Verify both deployed clients against the real Render endpoint before enabling access. Require a successful connection with the correct hostname and CA and a failed connection against a controlled wrong-name or untrusted-certificate test target. Record the TLS result, database, and role for each client without logging the URL. Repeat if Prisma or the database provider changes. The local probe tested TLS downgrade behavior only and did not contact a hosted database. [Render Postgres TLS](https://render.com/tutorials/postgres-on-render/connection-strings), [Prisma PostgreSQL URL parameters](https://docs.prisma.io/docs/orm/core-concepts/supported-databases/postgresql), [pinned migration engine parser](https://raw.githubusercontent.com/prisma/prisma-engines/d1b3f377ca835d73fd50954a5e22128b9ebdd6b8/quaint/src/connector/postgres/url.rs).

### Environment variable names

| Scope | Names and behavior |
| --- | --- |
| Express runtime | `NODE_ENV` set to production; `PORT`; `DATABASE_URL` with the runtime identity and `sslmode=verify-full`; `CORS_ORIGINS` empty for the same-origin browser, or a comma-separated list of exact approved HTTPS origins. |
| Authentication | `JWT_SECRET` is a unique secret per environment, at least 32 random bytes encoded in unpadded base64url. Set environment-specific `JWT_ISSUER` and `JWT_AUDIENCE`. Review `JWT_EXPIRES_IN`, `BCRYPT_ROUNDS`, `AUTH_RATE_WINDOW_MS`, `AUTH_SIGNUP_LIMIT`, and `AUTH_LOGIN_LIMIT`. Rotate JWT secrets with a planned sign-in reset. |
| Migration and verification jobs | `DATABASE_URL` for the migration identity in its job only, using the Prisma settings above; `TEST_DATABASE_URL` in local test jobs only. |
| Cloudflare connector and probe | `TUNNEL_TOKEN` for the connector. If using Access service credentials, store the client ID and secret in the probe system and send them only as `CF-Access-Client-Id` and `CF-Access-Client-Secret`. |
| Local development bootstrap | `BOOTSTRAP_DATABASE_TARGET`, `BOOTSTRAP_ORGANIZATION_NAME`, `BOOTSTRAP_ORGANIZATION_SLUG`, `BOOTSTRAP_ADMIN_NAME`, `BOOTSTRAP_ADMIN_EMAIL`, `BOOTSTRAP_ADMIN_PASSWORD`. See the [README](../README.md#provision-the-first-administrator). |

Keep credentials out of repo, build logs, image layers, command arguments, and browser settings. Runtime startup rejects production database URLs without `sslmode=verify-full` and rejects a process-wide TLS verification bypass. Treat connector-token rotation as a connector restart and revoke the old token. Preserve Express's default untrusted proxy setting. Verify Helmet CSP, HSTS, frame protection, and no-store authenticated responses through the edge. Before inviting testers, configure and test an approved edge IP throttle for login and signup, plus the existing application limiter. Cloudflare Free has limited rule matching; confirm the planned coverage against current plan limits. The in-memory limiter sees the connector's socket IP and may group testers into one bucket. Verify behavior from two authorized clients, including expected 429 responses and an ordinary workflow without lockouts. Agree on a shared or edge limiter design before scaling. [Cloudflare rate limiting limits](https://developers.cloudflare.com/waf/rate-limiting-rules/).

## Administrator provisioning and recovery

The shipped CLI is development-only. Keep its loopback and development guards in place. Before staging onboarding, approve and test an operator-only one-off job that uses the existing administrator bootstrap service and validator. Require a second operator to verify the provider/database identity and migration status. Verify the exact target and first-organization state before writing. Use a short-lived provisioning identity that can insert the organization, approved user and audit rows, without giving the application runtime organization-creation privileges. Pass a generated private password through a managed secret or masked prompt. Confirm the approval and bootstrap audit records, verify first sign-in, then revoke the temporary provisioning access and remove the job secrets. There is no web provisioning endpoint.

Recover access through an approved operator procedure. Confirm the administrator's identity, require two-person approval, and record the action. SafeOps does not ship password reset, an administrative password-change API, or production recovery tooling. Design and test an audited password-reset job that validates and hashes the new password, updates only the intended account and increments its authentication version in one transaction. Verify old-token rejection and retire the temporary permissions. Keep these jobs and the recovery rehearsal as deployment gates.

## Backups and monitoring

- Set recovery point and recovery time targets with the owner. Enable paid managed PITR and encrypted logical exports stored with separate access and retention. Render documents a 3-day Hobby and 7-day Pro-or-higher PITR window. Free instances have no managed recovery. Restore to a new isolated database and verify migration status, representative data and audit records, runtime grants, and the smoke workflow. Record recovery time and any data gap before considering a database cutover. [Render Postgres backups](https://render.com/docs/postgresql-backups).
- Render Private Services use TCP health checks. Run separate authenticated monitoring for `GET /api/v1/health` (liveness) and `GET /api/v1/ready` (database readiness). Gate a release on both returning 200 and prove that readiness returns 503 during a controlled staging outage. Alert on sustained readiness failures, error rates, rate-limit spikes, database connection/storage pressure, and backup failures. Keep access logs to method, route template, status and latency. Redact sensitive headers and responses from any edge or monitoring logs. Verify at least 10 seconds of process termination grace for the app's shutdown deadline. [Render health checks](https://render.com/docs/health-checks).

## Rollback checklist

- [ ] Freeze deployments. If Access, credentials, or tenant isolation may be affected, deny access at the edge and disable the tunnel route until containment is verified. Preserve redacted logs and record the failed commit, migration status, and last known-good artifact and configuration references.
- [ ] For an app-only fault, confirm the previous artifact supports the current schema and recovery can use current secret versions. Inspect Render's rollback preview before accepting it, because rollback can reuse deploy-time environment values. Redeploy or roll back to the known-good artifact only after verifying these inputs. Keep the database in place. [Render rollback behavior](https://render.com/docs/rollbacks).
- [ ] For a database fault or incompatible schema change, stop writes. Preserve the affected instance. Restore to a new isolated database, reapply runtime grants as needed, verify migration state and audit records, and record the data loss window. Obtain owner approval before reconciliation and cutover. Keep the previous database connection recoverable under controlled access.
- [ ] Verify the internal origin, TLS, liveness, readiness, Access denial, and the role-based smoke tests. Restore tester access only after the owner approves the evidence. Rotate any exposed credentials and verify revocation.

## Staging smoke tests

- [ ] From an unauthorized session verify Access denies `/app/` and API routes, and the origin cannot be reached directly. From an approved session verify HTTPS, health, readiness, headers, origin rules, and sanitized logs. Verify invalid credentials and test throttling in a controlled window.
- [ ] Provision a disposable administrator through the approved operator job. Sign in, approve an employee and an officer, and confirm tenants and roles. Check expiry and account revocation.
- [ ] Employee reports a hazard. Officer investigates, confirms and records a baseline assessment. Verify another organization cannot read the hazard, assessment, or action. Verify privileged controls are hidden from the employee.
- [ ] Officer assigns a corrective action. Employee starts work and submits completion. An independent manager verifies it. Verify a stale update requires reload and an assignee cannot self-verify.
- [ ] Officer records Low or Medium residual risk and closes the hazard. For an elevated fixture, escalate, record a new residual revision, and verify only an administrator can explicitly accept High or Critical risk and close it. Check that closed records are read-only.
- [ ] Repeat critical actions on a physical mobile device and by keyboard and screen reader. Capture redacted evidence and remove disposable staging data using an approved scoped process.
